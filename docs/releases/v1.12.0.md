SigardaPanel v1.12.0

Deploy from GitHub, GitLab and Gitea, a server switcher for multi-server panels, accurate server specifications, and a fix that makes git deploys work again.

Important fix
- Git deploys failed on real servers since v1.10.0 ("fork/exec git: permission denied"): every git step ran as the site's Linux user in a directory only the agent could enter. Deploys run as the site user in the site folder again.

Git integration (GitHub, GitLab, Gitea)
- Settings → Integrations: connect GitHub (including GitHub Enterprise), GitLab (gitlab.com or self-hosted) and Gitea accounts with an access token. Tokens are verified, stored encrypted and never sent to the servers.
- A site's new Git tab: pick an account, search your repositories (private ones too), pick the branch and connect. The panel creates a deploy key for the site on its server (as the site's Linux user; only the public key leaves the server), adds it read-only to the repository, adds a signed push webhook when the panel has a public https URL (SIGARDAPANEL_PUBLIC_URL), and runs the first deploy over SSH with pinned host keys. Any repository URL works too.
- Deploy pipeline: check out the branch (or a commit), then composer install, npm ci + npm run build, pip or go when the repository has them, then your deploy script (for example php artisan migrate --force). Everything runs as the site user; a failing step stops the deploy.
- Deploy history: status, commit, message, author, trigger (manual, push, rollback), duration and the full log (live while running), with redeploy and roll back to an earlier successful commit. The outcome shows on the commit in GitHub (deployments) or GitLab/Gitea (commit status). The site's deployed commit is recorded again.
- Pushes to other branches, branch deletions and sites with "Deploy on push" off do not deploy. Disconnecting removes the deploy key and webhook from the repository; the site's files stay.

Server switcher
- A switcher in the header chooses the server you work on (hidden with one server); the choice is remembered and can be shared with ?server=<id>.
- Docker, Firewall, Bot Blocker, PM2, Redis, Email, Monitoring and System use it (the per-page server menus are gone) and ask for a server under "All servers" instead of silently using the first one. Fail2ban, Threat Monitor, Terminal and Stack open the chosen server. Destructive confirmations name the server.
- Sites, Databases, Backups, Jobs and the Overview show only the chosen server (each row shows its server under All servers); Create site starts on it.

Server specifications
- Disk usage is shown for every filesystem on a disk (partitions, LVM), like df; loop, zram and CD-ROM devices are no longer listed; virtual disks are no longer reported as HDD.
- CPU: correct cache, clock on VMs, cores on ARM; commands run in the C locale.
- Installed RAM next to the usable amount; every IPv4/IPv6 address and MAC per interface without Docker bridges; virtual display adapters are not counted as GPUs.
- Cloud detection adds Tencent Cloud, Huawei Cloud, OVHcloud, Contabo, OpenStack and containers (LXC, OpenVZ), and the virtualization type.

Update the agents on remote servers after updating the panel (Settings → Panel update → Agents): the git integration, the deploy fix and the new specifications run on the agent.

Panels on v1.6.2 or older must update once by hand because of the new signing key (see the v1.7.1 notes):
  curl -fsSLO https://raw.githubusercontent.com/bayurstarcool/SigardaPanel/main/install.sh
  sudo bash install.sh update

Install with the script in the repository README; every file is signed (see "Verifying releases").
